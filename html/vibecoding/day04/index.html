4.서버 · 호스팅 · 배포 — 웹사이트는 어디에 있을까?

오늘부터 Supabase라는 "서버"를 사용합니다. 서버를 다루기 시작하면 서버, 트래픽, 스토리지 같은 단어가 계속 나옵니다. 코드를 몰라도 되지만, 이 단어들의 뜻은 알아야 AI에게 정확히 요청하고 요금표나 오류 메시지를 읽을 수 있습니다. 4~7번에서 하나씩 정리합니다.

서버 (Server)

요청을 받으면 필요한 것(웹페이지 파일, 데이터)을 보내 주는 컴퓨터입니다. 누가 언제 접속할지 모르기 때문에 하루 24시간 켜져 있고 인터넷에 연결되어 있습니다. 반대로 요청하는 쪽(내 휴대폰·PC의 브라우저)은 클라이언트(Client)라고 부릅니다.

웹사이트가 내 화면에 보이기까지

브라우저 주소창에 사이트 주소 입력 (클라이언트)
인터넷을 통해 서버에 "이 페이지 주세요" 요청
서버가 HTML · CSS · JavaScript · 이미지 파일을 보내 줌
브라우저가 받은 파일로 화면을 그림
비유하자면 — 식당과 같습니다. 손님(클라이언트)이 주문하면 주방(서버)이 음식(파일·데이터)을 만들어 내보냅니다. 손님은 주방 안을 몰라도 주문서만 정확하면 원하는 음식을 받을 수 있습니다.

지금 내 사이트는 누가 볼 수 있을까?

지금 (DAY 03까지)

파일이 내 컴퓨터 안에만 있습니다. 브라우저 주소창이 file:///C:/...나 127.0.0.1로 시작하면 나만 볼 수 있는 상태입니다. 친구에게 주소를 보내도 열리지 않습니다.

배포한 뒤

파일이 서버에 올라가 있어서, https://...로 시작하는 주소만 알면 누구나 어디서든 볼 수 있습니다.

호스팅 (Hosting)

서버를 직접 사서 24시간 관리하는 대신, 업체의 서버 공간을 빌려 쓰는 것입니다. 가게를 지을 때 건물을 짓지 않고 상가를 임대하는 것과 같습니다.

배포 (Deploy)

내 컴퓨터에서 만든 파일을 서버에 올려서 다른 사람이 볼 수 있게 공개하는 일입니다. 임대한 상가에 물건을 채우고 문을 여는 "개업"에 해당합니다.

5.데이터베이스 · 스토리지 · 메모리 — 무엇을 어디에 둘까?

서버 요금표를 보면 "Database 500MB", "Storage 1GB", "메모리 256MB"처럼 저장 공간이 여러 종류로 나뉘어 있습니다. 모두 "저장"과 관련 있지만 하는 일이 다릅니다.

데이터베이스 (Database)

글자와 숫자를 표 형태로 정리해 두는 곳. 찾기·고치기·정렬하기가 빠릅니다.

비유 — 가게의 장부
예 — 메뉴 이름, 가격, 회원 이메일, 문의 내용

스토리지 (Storage)

사진·영상·PDF 같은 파일 자체를 보관하는 곳. "저장공간"이라고도 씁니다.

비유 — 가게의 창고
예 — 메뉴 사진 파일, 프로필 사진, 첨부 파일

메모리 (Memory · RAM)

서버가 지금 처리 중인 일을 잠깐 올려 두는 곳. 서버가 꺼지면 내용이 사라집니다.

비유 — 주방의 작업대
클수록 동시에 많은 요청을 처리할 수 있음

메뉴 하나는 어디에 저장될까?

정보 저장 위치
Cream Latte, 6500, 설명 글데이터베이스 (오늘 만들 menus 표)
cream-latte.jpg 사진 파일스토리지 (오늘은 간단하게 프로젝트의 images 폴더 사용)
그 사진이 있는 위치(주소)데이터베이스의 image_url 칸

장부(데이터베이스)에는 사진을 붙이지 않고 "창고 몇 번 선반에 있음"처럼 위치만 적습니다. 그래서 사진은 스토리지에, 사진 주소는 데이터베이스에 따로 저장됩니다.

용량 단위 감 잡기

KB(킬로바이트) < MB(메가바이트) < GB(기가바이트) — 각각 약 1,000배씩 커집니다.

  • • 메뉴 한 줄(이름·가격·설명) — 1KB도 안 됨. 메뉴 1만 개도 데이터베이스에서는 몇 MB
  • • 웹용으로 줄인 사진 한 장 — 약 0.2MB / 휴대폰 원본 사진 — 3~5MB
  • • 그래서 용량을 차지하는 것은 대부분 사진과 영상입니다. 사이트에 올릴 사진은 줄여서 쓰는 습관이 중요합니다.

6.트래픽 · 동시접속 — 손님이 몰리면 어떻게 될까?

트래픽 (Traffic · 데이터 전송량)

서버와 방문자 사이에 오고 간 데이터의 양입니다. 누군가 내 사이트를 열 때마다 서버는 HTML·이미지 파일을 보내 주고, 그만큼 트래픽이 쌓입니다. 원래 뜻이 "도로 위 교통량"이듯, 서버로 드나드는 데이터의 통행량이라고 생각하면 됩니다. 요금표에서는 전송량, 대역폭(Bandwidth), Egress(내보낸 양)라고도 씁니다.

계산해 보기 — 하루 트래픽은 얼마나 될까?

원본 사진을 그대로 쓴 사이트

한 번 열 때 약 15MB (사진 3장 × 5MB)
× 하루 방문 1,000번
= 하루 약 15GB

사진을 웹용으로 줄인 사이트

한 번 열 때 약 1MB (사진 3장 × 0.2MB + 기타)
× 하루 방문 1,000번
= 하루 약 1GB

같은 사이트라도 사진 크기에 따라 트래픽이 10배 넘게 차이 납니다. 사진을 줄이면 사이트도 빨리 열리고 서버 비용도 아낄 수 있습니다.

동시접속 (Concurrent Users)

같은 순간에 사이트를 쓰고 있는 사람 수입니다. 하루 방문자와는 다릅니다. 하루 1,000명이 와도 시간이 흩어져 있으면 동시접속은 10명 안팎일 수 있습니다. 식당으로 치면 하루 손님 수가 아니라 좌석 수에 해당합니다.

한도를 넘으면 어떻게 될까? — 서비스마다 다름

추가 요금넘은 만큼 돈을 더 냄
속도 제한사이트가 느려짐
대기열손님이 순서를 기다림
일시 정지사이트가 잠시 멈춤

예를 들어 DAY 05에 사용할 카페24 AI SPACE 무료 체험은 동시접속 25명까지이고, 넘으면 대기열로 안내된다고 소개되어 있습니다. 수업에서 만드는 사이트는 한도에 걸릴 일이 거의 없지만, 서비스를 고를 때 "트래픽 · 동시접속 한도와 넘었을 때 어떻게 되는지"를 꼭 확인하세요.

7.API · API 키 — 서버에 요청하는 창구와 출입증

API (Application Programming Interface)

프로그램끼리 정해진 방식으로 요청하고 답을 받는 창구입니다. 은행 창구에서 정해진 서식에 맞춰 써 내면 직원이 처리해 주듯, 내 웹사이트의 JavaScript가 Supabase의 API에 "menus 표의 메뉴를 보여줘"라고 요청하면 Supabase가 데이터를 보내 줍니다.

내 웹사이트 (JavaScript) → 요청 + API 키 → Supabase API (창구) → 메뉴 데이터 응답

API 키 (API Key)

창구에 요청할 때 함께 내미는 출입증입니다. 아무나 요청하지 못하게 하고, 누가 요청했는지 구분하는 데 씁니다. 긴 영문·숫자 문자열로 되어 있습니다.

공개용 키 (Supabase: Publishable Key)

손님용 출입증. 웹사이트 코드에 들어가므로 누구나 볼 수 있다는 전제로 만들어졌습니다.

대신 이 키로 할 수 있는 일은 RLS(접근 규칙)로 제한합니다 — 예: "메뉴 보기만 허용". 그래서 STEP 05에서 규칙을 먼저 정합니다.

비밀용 키 (Supabase: Secret Key)

사장님 마스터키. 모든 규칙을 무시하고 데이터를 읽고, 고치고, 지울 수 있습니다.

HTML·JavaScript 파일, GitHub, 채팅방, 캡처 화면 어디에도 절대 올리지 않습니다. 실수로 노출됐다면 Supabase에서 바로 새 키로 바꿉니다.

기억할 것 — 공개용 키는 보여도 괜찮게 설계된 키, 비밀용 키는 보이면 안 되는 키. AI에게 연결을 요청할 때도 "Secret Key는 사용하지 마"를 꼭 붙입니다.

9.SQL이란? · AI에게 SQL 요청하는 방법

SQL (Structured Query Language, 구조화 질의 언어)

Database에 데이터를 만들고, 저장하고, 찾고, 수정하고, 삭제하도록 요청할 때 사용하는 언어. Database가 "창고"라면 SQL은 창고에 일을 시키기 위한 언어입니다.

사람의 말과 SQL 비교하기

사람이 말한다면

"menus에 있는 모든 메뉴를 보여줘."

SQL에서는 
SELECT * FROM menus;
사람이 말한다면

"Strawberry Latte라는 새로운 메뉴를 저장해줘."

SQL에서는 
INSERT INTO menus (name, price)
VALUES ('Strawberry Latte', 7000);

우리가 직접 SQL을 외워 작성하지 않아도, AI에게 "무엇을 하고 싶은지" 정확하게 알려주면 필요한 SQL을 작성하도록 요청할 수 있습니다.

SQL로 할 수 있는 기본 작업 & CRUD

SELECT

데이터 가져오기

"보여줘." · Read

INSERT

새로운 데이터 추가하기

"추가해줘." · Create

UPDATE

기존 데이터 수정하기

"바꿔줘." · Update

DELETE

기존 데이터 삭제하기

"지워줘." · Delete

오늘 실제로 사용할 것 — CREATE TABLE(Table 만들기), INSERT(메뉴 추가), SELECT(메뉴 확인), UPDATE(메뉴 수정). DELETE는 개념만 알아두고 오늘 핵심 실습에서는 사용하지 않습니다.

12.STEP 05. 웹사이트에서 메뉴를 읽을 수 있도록 권한 설정하기

RLS (Row Level Security, 행 단위 보안)

Database에 저장된 데이터에 누가 어떤 작업을 할 수 있는지 제한하는 보안기능입니다. MELLOW BEAN 사이트를 방문한 사람은 메뉴를 보는 것은 가능하지만, 가격을 마음대로 바꾸거나 메뉴를 삭제하면 안 됩니다.

메뉴 보기 — 허용 (O)
메뉴 추가·수정·삭제 — 불허 (X)

메뉴 관리(추가·수정)는 방문자가 아니라 Supabase Dashboard SQL Editor에서 관리자가 직접 진행합니다.

16.SQL 사용 시 주의할 점 & 문제 해결하기

AI가 만들어준 SQL = 무조건 안전한 코드 X

실행 전에 최소한 무슨 작업인지 확인합니다. 특히 DELETE, DROP, UPDATE처럼 기존 데이터에 영향을 줄 수 있는 SQL은 어떤 데이터를 대상으로 하는지 더 주의해서 확인합니다.

SELECT → 조회 INSERT → 추가 UPDATE → 수정 DELETE → 삭제 DROP → 구조 삭제 가능

Database에는 메뉴가 있는데 웹사이트에 안 나온다면?

한꺼번에 모든 코드를 다시 만들지 않고, 아래 순서대로 확인합니다.

Supabase Table에 데이터가 있는가?
RLS와 SELECT Policy가 있는가?
Project URL이 맞는가?
Publishable Key가 맞는가?
JavaScript에서 menus를 요청하고 있는가?
Browser Console에 오류가 있는가?

STEP 12

메뉴 가격 수정하기

이번에는 새로운 데이터 추가가 아니라 기존 데이터 수정입니다 — Cream Latte 가격을 6,500원에서 6,800원으로 변경합니다.

확인할 단어 — UPDATE + WHERE. WHERE는 "어떤 데이터에 작업할 것인지" 조건을 지정합니다 — 조건 없이 UPDATE하면 모든 데이터가 바뀔 수 있으니 항상 확인하는 습관을 들입니다.

STEP 13

X 좋지 않은 요청

"가격 바꾸는 SQL 만들어줘."

O 개선한 요청

"Supabase의 menus Table에서 Cream Latte의 price만 6800으로 변경하는 SQL을 만들어줘. 다른 Row는 수정하지 마. WHERE 조건을 사용해서 Cream Latte만 수정되도록 해줘. 실행 전에 어떤 데이터를 수정하는 코드인지 설명해줘."

핵심 — SQL을 잘 요청하려면 SQL 문법보다 현재 데이터 구조와 원하는 작업을 정확하게 설명하는 능력이 중요합니다.
