02
Core Web Terms

UI 용어 ① Header · Navigation

"위에 있는 거 조금 작게 해줘"보다 "Header의 높이를 줄여줘"가 훨씬 정확합니다. 오늘의 목표는 코드를 외우는 것이 아니라 화면에서 수정하고 싶은 부분의 이름을 알고 말할 수 있는 것입니다.

Header (헤더)

웹페이지 가장 위쪽 영역. 주로 Logo, Navigation, 로그인·문의·메뉴 버튼이 위치

"Header의 높이를 조금 줄여줘."

Navigation (내비게이션, Nav)

사용자가 주요 페이지나 Section으로 이동할 수 있도록 만든 메뉴

"모바일에서 Navigation이 화면 밖으로 벗어나지 않게 해줘."

03
Core Web Terms

UI 용어 ② Hero Section · Section · CTA · Button

Hero Section (히어로 섹션)

웹사이트에 들어왔을 때 가장 먼저 크게 보이는 대표 영역. 주로 메인 제목, 설명, 대표 이미지, CTA Button으로 구성

Section (섹션)

웹페이지 안에서 하나의 목적을 가지고 구성된 영역. 예: About, Portfolio, Menu, Contact Section

CTA (Call To Action)

사용자에게 다음 행동을 유도하는 버튼·링크. 예: [문의하기] [프로젝트 보기] [신청하기]

Button

클릭하면 특정 행동이 실행되는 UI 요소. Button은 클릭 가능한 요소 자체, CTA는 그중 중요한 행동을 유도하는 역할

04
Core Web Terms

UI 용어 ③ Card · Form · Footer

Card (카드)

관련 정보를 하나로 묶어 보여주는 UI 요소. 상품, 메뉴, Portfolio, 게시글 등에 활용

Form / Input / Textarea

사용자의 정보를 입력받는 영역. Input(한 줄 입력창)은 이름·이메일, Textarea(여러 줄)는 문의내용·후기 등에 사용

Footer (푸터)

웹사이트 가장 아래에 위치. 회사정보, 연락처, Copyright, SNS, 관련 링크 등이 위치

웹페이지 기본 구조 한 번에 보기 — Header → Navigation → Hero → Content Section → Card/Image/Text → CTA → Form → Footer
05
Better Prompting

용어를 알면 프롬프트가 달라진다

용어를 모를 때

"맨 위에 메뉴 있는 부분이 너무 커. 조금 줄여줘." / "가운데 네모 3개 사이를 좀 벌려줘."

용어를 알고 있을 때

"Header의 높이를 조금 줄여줘. Navigation 글자 크기는 유지하고 Padding만 줄여줘." / "Portfolio Section의 Card 3개 사이 Gap을 넓혀줘. Card 크기는 유지해줘."

오늘의 공통 미션 — 개인 프로젝트를 제작하면서 오늘 배운 용어(Header, Navigation, Hero, Section, CTA, Button, Card, Form, Footer) 중 최소 3개 이상을 직접 프롬프트에 사용하기

STEP 01~03. Wireframe 점검 · 콘텐츠 정리 · BUILD_SPEC

STEP 01

Wireframe 최종 점검하기

프롬프트 01
상자를 클릭하면 바로 복사돼요

지금부터 DAY 05에서 기획한 개인 프로젝트를 실제로 제작하려고 해. 먼저 현재 PROJECT_PLAN.md와 wireframe.html을 확인해줘. 아직 실제 웹사이트 코드는 작성하지 마. 다음 항목만 점검해줘. 1. 프로젝트 목적과 Wireframe이 일치하는지 2. Must Have 기능에 필요한 화면이 모두 있는지 3. User Flow에서 필요한 Button과 CTA가 Wireframe에 존재하는지 4. 불필요한 Section이 있는지 5. 사용자가 행동을 진행하다가 막히는 부분이 있는지 문제가 있다면 먼저 문제점을 알려줘. 수정이 꼭 필요한 부분만 제안해줘. 프로젝트의 범위를 새롭게 키우지는 마.

핵심 — 새 기능 추가 제안이 나와도 "정말 필요한가?"를 먼저 판단하고, 필요하지 않다면 추가하지 않습니다.

STEP 02

실제 콘텐츠 준비상태 확인하기

프롬프트 02
상자를 클릭하면 바로 복사돼요

PROJECT_PLAN.md와 wireframe.html을 기준으로 실제 웹사이트 제작에 필요한 콘텐츠를 체크리스트로 정리해줘. 다음 항목으로 나누어줘. 1. 필요한 텍스트 2. 필요한 이미지 3. 필요한 Button 문구 4. 필요한 Contact 정보 5. Database를 사용하는 경우 필요한 데이터 이미 결정된 내용과 아직 준비되지 않은 내용을 구분해줘. 새로운 콘텐츠를 임의로 만들어내지는 마.

오늘 모든 콘텐츠를 완벽히 준비하지 않아도 됩니다. 부족한 부분은 임시 콘텐츠를 쓰고 나중에 교체 가능하지만, 대표 이미지·프로젝트명·핵심문구 정도는 가능하면 준비합니다.

BUILD_SPEC (Build Specification, 제작 명세서) — PROJECT_PLAN(무엇을 만들 것인가) → Wireframe(어떻게 배치할 것인가) → BUILD_SPEC(실제로 무엇을 어떻게 구현할 것인가)

프롬프트 03
상자를 클릭하면 바로 복사돼요

현재 PROJECT_PLAN.md와 wireframe.html을 기준으로 실제 개발에 사용할 BUILD_SPEC.md 파일을 만들어줘. 다음 내용을 포함해줘. 1. 프로젝트 이름 2. 프로젝트 목적 3. 주요 사용자 4. Must Have 기능 5. Nice to Have 기능 6. 전체 Page 또는 Section 구조 7. 각 Section에 들어갈 콘텐츠 8. Navigation 구조 9. Button과 CTA의 기능 10. 필요한 이미지 11. Database 사용 여부 12. Database가 필요한 경우 Table과 주요 데이터 13. Desktop 기본 Layout 14. Mobile에서 고려할 내용 아직 실제 프로젝트 코드는 작성하지 마. PROJECT_PLAN에 없는 새로운 기능은 추가하지 말고 지금까지 확정한 내용만 정리해줘.

핵심 — BUILD_SPEC가 완성된 뒤 개발을 시작합니다.

STEP 05

프로젝트 기본구조 만들기

프롬프트 05
상자를 클릭하면 바로 복사돼요

이제 BUILD_SPEC.md를 기준으로 실제 프로젝트 제작을 시작해줘. 이번 단계에서는 프로젝트의 기본구조만 만들어줘. 필요한 HTML, CSS, JavaScript 파일과 기본 폴더를 생성해줘. BUILD_SPEC에 정의된 Page와 Section이 모두 들어갈 수 있는 기본 HTML 구조를 만들어줘. 아직 세부 디자인, Animation, Hover, Database 연결은 하지 마. 임시 콘텐츠를 사용할 경우 실제 콘텐츠와 구분할 수 있도록 작성해줘. 코드는 초보자가 이후 수정하기 쉽도록 지나치게 복잡하게 만들지 마. 작업이 끝나면 어떤 파일을 생성하거나 수정했는지 알려줘.

결과 확인 — 지금은 디자인이 아니라 필요한 Page/Section, Header, Footer가 있는지, 순서가 Wireframe과 맞는지 뼈대만 확인합니다.

STEP 06

Header와 Navigation 구현하기

프롬프트 06
상자를 클릭하면 바로 복사돼요

BUILD_SPEC와 Screen Flow를 기준으로 Header와 Navigation을 구현해줘. Navigation에는 기획서에 정의된 메뉴만 사용해줘. 메뉴를 클릭했을 때 연결되어야 하는 Page 또는 Section으로 이동하도록 만들어줘. 현재 단계에서는 Header 디자인을 지나치게 화려하게 만들지 말고 기본적인 형태로 구현해줘. 다른 Section의 세부 디자인은 수정하지 마.

확인 — 메뉴 직접 클릭 → 정확한 위치로 이동하는지. 예시 수정 프롬프트: "Header의 높이가 조금 커 보여. Navigation의 Font Size는 유지하고 Header의 위아래 Padding만 조금 줄여줘. 다른 Section은 변경하지 마."

프롬프트 07

BUILD_SPEC와 Wireframe을 기준으로 Hero Section을 구현해줘. 프로젝트의 실제 제목과 핵심 설명을 적용해줘. Wireframe에 대표 이미지 영역이 있다면 이미지가 들어갈 위치를 만들어줘. CTA가 있다면 Screen Flow에 정의된 기능과 연결해줘. 아직 다른 Section의 디자인은 수정하지 마. Hero Section만 구현해줘.

결과 확인하기
사이트 목적이 첫 화면에 보이는가? 제목이 적절한가? 설명이 너무 길지 않은가? CTA가 필요한 위치에 있는가? CTA가 실제 행동으로 연결되는가?

수정 예시 — "Hero Section의 메인 제목을 현재보다 조금 크게 만들어줘. 설명과 CTA의 크기는 유지해줘. 다른 Section은 수정하지 마." 또는 "Hero Section의 이미지 영역이 너무 커 보여. 전체 Layout은 유지하고 이미지 영역의 너비만 조금 줄여줘."

프롬프트 08

Card가 있다면 — "Product Section의 Card 3개 높이를 동일하게 맞춰줘. Card 안의 이미지 영역 크기도 동일하게 만들어줘. Card 사이 간격은 일정하게 유지해줘."

상자를 클릭하면 바로 복사돼요

현재 프로젝트에서 임시 텍스트와 임시 이미지 영역을 확인해줘. 내가 준비한 실제 콘텐츠를 아래 위치에 적용해줘. [실제 콘텐츠 입력] 현재 Layout과 Section 구조는 유지해줘. 콘텐츠 교체와 관계없는 디자인은 변경하지 마.

실제 이미지를 넣을 경우 — images 폴더에 파일 추가 후: "images 폴더에 실제 이미지를 추가했어. [파일명]은 [Section 이름]에 사용해줘. 이미지가 찌그러지지 않도록 비율을 유지해줘. 기존 Layout과 콘텐츠는 변경하지 마."

First Feature

STEP 11. Must Have 기능 구현 시작하기

화면만 완성되어도 프로젝트가 끝난 것은 아닙니다 — 문의하기 Button이 있어도 실제로 작동하는지, 신청 Form이 데이터를 저장하는지 확인이 필요합니다. 보이는 것과 작동하는 것은 다릅니다.

프롬프트 11
상자를 클릭하면 바로 복사돼요

BUILD_SPEC에 정의된 Must Have 기능 중 첫 번째 기능을 구현하려고 해. 구현할 기능은 "[기능 이름]"이야. 현재 프로젝트 구조를 먼저 확인하고 이 기능에 필요한 파일만 수정해줘. 이미 정상적으로 작동하고 있는 다른 기능과 Section은 변경하지 마. 기능을 구현한 뒤 내가 어떤 방법으로 정상작동 여부를 테스트하면 되는지도 알려줘.

Database 기능이 필요하다면 DAY 04에서 배운 방식을 그대로 활용합니다 — 현재 Database 구조 + 필요한 작업 + 저장할 데이터 + 수정하면 안 되는 범위를 AI에게 설명 → SQL 생성 → 역할 확인 → Supabase에서 실행. 바로 SQL 만들기 전에 데이터 구조부터 확인하는 것이 핵심입니다.

STEP 12. 현재 진행상태 점검하기

DAY 06에서 모든 기능을 완성할 필요는 없습니다. 오늘의 목표는 기본구조, 주요 Section, 실제 콘텐츠 일부, 첫 번째 Must Have 기능까지입니다.

프롬프트 12
상자를 클릭하면 바로 복사돼요

BUILD_SPEC.md와 현재 프로젝트를 비교해서 지금까지의 개발 진행상태를 점검해줘. 다음 세 가지로 구분해줘. 1. 완료된 작업 2. 아직 구현되지 않은 Must Have 3. 구현은 되었지만 테스트가 필요한 기능 새로운 기능은 제안하지 마. 현재 기획된 프로젝트를 완성하는 데 필요한 작업만 정리해줘. 그리고 다음에 진행해야 할 작업을 우선순위 순서로 정리해줘.

지금 하지 않을 것 — 화려한 Animation, 복잡한 Slider, 추가 Page, 좋아요 기능, 새로운 Database Table, 불필요한 Popup. Must Have가 완성되지 않은 상태에서 기능을 계속 추가하면 프로젝트가 완성되지 않을 가능성이 높아집니다.
