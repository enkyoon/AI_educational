DAY 08. 최종 프로젝트 완성

오늘은 새로운 기능을 많이 만드는 날이 아니라, 지금까지 만든 것을 완성하는 날입니다. 디자인 디테일을 정리하고 Desktop·Mobile을 최종 검증한 뒤 발표 가능한 완성본을 만듭니다.

01
Orientation

수업 구성 · 오늘의 가장 중요한 원칙

수업방식

공통 이론(UI·디자인 용어, 15~20분) + 디자인 디테일 수정 + 최종 QA + 발표 준비 + 프로젝트 발표

핵심목표

디자인 디테일과 콘텐츠를 정리하고, Desktop·Mobile·기능을 최종 검증한 뒤 발표 가능한 완성본 만들기

DAY 08에서 자주 발생하는 실수 — "마지막 날이니까 기능 하나 더 넣어볼까?" → 새 기능 추가 → 예상 못한 오류 → 기존 기능까지 깨짐 → 발표 직전까지 수정

오늘은 반대로 — 새 기능 추가 STOP → 현재 기능 안정화 → 디자인 정리 → 콘텐츠 확인 → 전체 테스트 → 발표 준비

🎯 마지막 날은 더 많이 만드는 날이 아니라, 지금까지 만든 것을 완성하는 날입니다.

02
Design Terms

디자인 용어 ① Typography · Visual Hierarchy

DAY 06은 "무엇을 수정할 것인지"(Header, Card, Form), DAY 07은 "어떻게 배치할 것인지"(Container, Grid), DAY 08은 "어떻게 더 완성도 있게 보이게 할 것인지"를 배웁니다.

Typography

Font Family, Font Size, Font Weight, Line Height, Letter Spacing으로 글자를 구성하는 것. 하나의 사이트에서 너무 많은 Font를 쓰지 않고, 제목+본문 정도의 명확한 체계를 유지합니다.

Visual Hierarchy (시각적 위계)

정보의 중요도를 크기·굵기·색상·여백·위치로 구분하는 방식. 질문: 웹사이트를 처음 본 사람이 5초 안에 "무엇을 하는 곳인지" 알 수 있는가?

중요도 순서 — Hero Title → CTA → Section Title → 본문
03
Design Terms

디자인 용어 ② Border · Border Radius · Shadow · Opacity

Border

Card·Button·Input의 경계를 보여주는 선. 너무 많으면 화면이 복잡해지니 필요한 영역에만 사용

Border Radius

모서리의 둥글기. 작으면 단정하고 각진 느낌, 크면 부드럽고 친근한 느낌 — 전체 사이트에서 비슷한 체계 유지

Shadow

요소가 배경과 구분되도록 돕는 그림자 효과. 원칙 — 필요한 곳에 약하게 사용

Opacity

투명도(1=완전히 보임, 0=안 보임). 배경 이미지 위 Overlay, 보조 Text에 활용. 본문 Text는 지나치게 낮추지 않기

04
Design Terms

디자인 용어 ③ Hover · Transition · Icon · Modal

좋은 Hover

Button 배경색 조금 변경, Card 살짝 올라옴, Navigation 글자색 변경

좋지 않은 Hover

Card가 지나치게 확대, Button이 크게 흔들림, Layout 자체가 움직임

Transition

Hover 등의 상태 변화가 즉시가 아니라 부드럽게 이어지도록 만드는 효과

Icon

기능이나 의미를 작은 그림으로 표현. 장식용으로 무작정 추가하지 않고, 보면 기능을 이해할 수 있어야 함

핵심 — Interaction은 기능을 방해하지 않을 정도로 사용. Modal은 이미 있는 프로젝트의 디자인 수정 시에만 활용하고 DAY 08에 새로 추가하지 않습니다.

STEP 02

AI에게 Feature Freeze 기준 전달하기

Feature Freeze (기능 동결)

프로젝트 마무리 단계에서 새로운 기능 추가를 멈추고 현재 기능을 안정화하는 것. 발표 직전에는 기능의 개수보다 안정적으로 작동하는 것이 중요합니다.

프롬프트 02
상자를 클릭하면 바로 복사돼요

지금부터 이 프로젝트는 Feature Freeze 단계로 진행할 거야. 새로운 Page, Section, 기능, Database 기능은 추가하지 마. 현재 구현되어 있는 기능과 디자인을 안정적으로 완성하는 데만 집중해줘. 이후 내가 수정 요청을 하더라도 요청하지 않은 새로운 기능은 임의로 추가하지 마.

Typography Polish

STEP 03. Typography 최종 정리하기

프롬프트 03
상자를 클릭하면 바로 복사돼요

현재 프로젝트의 Typography만 전체적으로 점검해줘. 다음 항목을 확인해줘. 1. Hero Title 2. Section Title 3. Card Title 4. Body Text 5. Button Text 6. Navigation 정보의 중요도에 따라 Font Size와 Font Weight가 자연스럽게 구분되는지 확인해줘. 본문의 Line Height도 읽기 편한지 확인해줘. 너무 많은 Font Size나 Font Weight가 사용되고 있다면 일관되게 정리해줘. 기존 콘텐츠, Layout, 기능은 변경하지 마.

가장 중요한 제목이 먼저 보이는가? Section 제목이 본문과 구분되는가? 본문이 읽기 편한가? Button Text가 너무 작지 않은가?

Consistency

STEP 04~05. UI 일관성 · Card 디테일 정리하기

Consistency (일관성)

같은 역할의 Button, Card, Input, Title 등은 비슷한 디자인 규칙을 사용해야 합니다. Button마다 둥글기가 4px, 20px, 완전 둥근 형태로 제각각이면 일관성이 떨어져 보입니다.

STEP 04

UI 일관성 점검하기

프롬프트 04
상자를 클릭하면 바로 복사돼요

현재 프로젝트의 UI 디자인 일관성을 점검해줘. 특히 Button, Card, Input, Textarea를 확인해줘. 같은 역할의 요소는 Border, Border Radius, Padding, Font 등의 규칙이 일관되도록 정리해줘. 전체 디자인을 새롭게 바꾸지 말고 현재 스타일을 기준으로 통일해줘. 기능과 Layout은 변경하지 마.

STEP 05

Card 디테일 점검하기 (Card가 있는 경우)

프롬프트 05
상자를 클릭하면 바로 복사돼요

현재 프로젝트의 Card 디자인만 점검해줘. Card의 Border, Border Radius, Shadow, 내부 Padding이 전체 사이트 디자인과 잘 어울리는지 확인해줘. 지나치게 강한 Border나 Shadow가 있다면 조금 정리해줘. Card Layout과 콘텐츠는 변경하지 마.

목표 — 정보는 구분되지만 디자인은 과하지 않게

Interaction

STEP 06. Hover · Transition 적용하기

기본 디자인이 정리되었다면 클릭 가능한 요소의 Interaction을 확인합니다. 모든 요소에 적용할 필요는 없습니다.

프롬프트 06
상자를 클릭하면 바로 복사돼요

현재 프로젝트에서 사용자가 클릭하거나 선택할 수 있는 요소의 Hover 상태를 점검해줘. Navigation, Button, 클릭 가능한 Card나 Link에 필요한 경우 자연스러운 Hover 효과를 적용해줘. 색상 변화나 아주 작은 움직임 정도의 절제된 효과만 사용해줘. Hover 변화가 자연스럽게 이어지도록 필요한 곳에 Transition을 적용해줘. Layout이 움직일 정도로 강한 효과는 사용하지 마. 기능은 변경하지 마.

직접 확인 — Navigation → Button → Card 순서로 마우스를 올려보며 클릭 가능한지 알아보기 쉬운지, 효과가 과하지 않은지, 화면이 흔들리지 않는지 확인합니다.

지금까지 만든 프로젝트를 발표하려고 해. BUILD_SPEC.md와 현재 프로젝트를 기준으로 발표 내용을 정리해줘. 다음 순서로 구성해줘. 1. 프로젝트 이름 2. 프로젝트 한 줄 소개 3. 주요 사용자 4. 프로젝트 목적 5. 핵심기능 3개 정도 6. 실제 Demo 순서 7. Claude Code와 AI를 활용한 과정 8. 제작 중 발생했던 문제와 해결과정 실제 프로젝트에 존재하지 않는 기능이나 경험은 만들어내지 마. 발표자가 자연스럽게 설명할 수 있도록 핵심내용 중심으로 정리해줘.

발표 직전 하지 않을 것 — 새로운 기능 추가, 대규모 디자인 변경, Database 구조 변경, 전체 코드 재작성. 허용되는 것은 명확한 오타, 깨진 이미지, 작동하지 않는 Button 등 발표를 막는 오류를 최소한으로 고치는 것뿐입니다. Demo도 첫 화면 → Button → 기능 → Database → Mobile 순서로 미리 한 번 실행해보고 어디를 클릭할지 결정해둡니다.

Final Message

과정 최종 메시지

바이브코딩은 AI에게 "웹사이트 만들어줘"라고 말하는 것만을 의미하지 않습니다. 실제 과정은 무엇을 만들지 결정 → 사용자의 흐름 설계 → 화면구조 설계 → AI에게 작업 요청 → 결과 확인 → 문제 발견 → 수정범위 지정 → Debugging → Database 연결 → Responsive 확인 → QA → 완성입니다.

AI가 코드를 작성하더라도, 프로젝트의 방향을 결정하고 결과를 판단하고 수정할 내용을 지시하는 것은 사람의 역할입니다.
