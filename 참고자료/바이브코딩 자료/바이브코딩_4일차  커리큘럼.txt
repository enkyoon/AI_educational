# 01. 오늘 바꿀 방식

지금 메뉴 4줄은 HTML 안에 직접 적혀 있다. 메뉴가 30개라면? 새 메뉴마다 HTML을 열고 → 줄 복사 → 내용 바꾸기 → 저장.
오늘 바꿀 방식 : 메뉴 정보는 Database에 → 웹사이트가 가져와서 → 메뉴 줄을 자동으로 만든다.
새 메뉴 = Database에 한 줄 추가 → 새로고침.
핵심 — 모양(메뉴 한 줄의 디자인)은 웹사이트가, 내용(이름 · 가격)은 Database가 맡는다.

# PART 서버 기본 개념

오늘부터 Supabase라는 "서버"를 쓴다. 코드는 몰라도 되지만 단어 뜻은 알아야 AI에게 정확히 요청하고 요금표 · 오류 메시지를 읽을 수 있다.

# 02. 서버 · 호스팅 · 배포 (8분)

- 서버 : 요청을 받으면 웹페이지 파일 · 데이터를 보내 주는, 24시간 켜진 컴퓨터. 요청하는 쪽(내 브라우저)은 클라이언트
- 흐름 : 주소 입력 → 서버에 "이 페이지 주세요" → 서버가 HTML · CSS · JS · 사진을 보냄 → 브라우저가 화면을 그림
- 비유 — 식당. 손님(클라이언트)이 주문하면 주방(서버)이 음식(파일 · 데이터)을 내보낸다
- 지금 내 사이트 : 주소창이 file:/// 나 127.0.0.1 → 내 컴퓨터 안에만 있어서 나만 볼 수 있음 / 배포한 뒤 : https:// 주소만 알면 누구나
- 호스팅 : 서버를 직접 사는 대신 업체의 서버 공간을 빌려 쓰는 것 — 상가 임대
- 배포 : 내 컴퓨터의 파일을 서버에 올려 공개하는 일 — 개업
- 이 과정에서 만날 서버 : Supabase(데이터 · 회원 · 주문 — DAY 04~08), GitHub Pages(웹사이트 공개 — DAY 08)

# 03. 데이터베이스 · 스토리지 · 메모리 (7분)

요금표에 "Database 500MB", "Storage 1GB", "메모리 256MB"처럼 나뉘어 있다.
- 데이터베이스 : 글자 · 숫자를 표로 정리 — 가게 장부 (메뉴 이름, 가격, 회원 이메일)
- 스토리지 : 사진 · 영상 · PDF 파일 자체 — 창고 (메뉴 사진)
- 메모리(RAM) : 서버가 지금 처리 중인 일을 잠깐 올려 두는 곳, 꺼지면 사라짐 — 주방 작업대
메뉴 하나는? Cream Latte · 6500 · 설명 → 데이터베이스 / cream-latte.jpg → 스토리지(오늘은 images 폴더) / 사진 위치 → 데이터베이스 image_url 칸
장부에는 사진을 붙이지 않고 "창고 몇 번 선반"처럼 위치만 적는다.
용량 : KB < MB < GB (약 1,000배씩). 메뉴 한 줄 1KB 미만 / 웹용 사진 약 0.2MB / 휴대폰 원본 3~5MB (DAY 03의 카카오톡 사진 2.8MB를 기억)

# 04. 트래픽 · 동시접속 (6분)

- 트래픽 : 서버와 방문자 사이에 오고 간 데이터 양. 요금표에서는 전송량 · Bandwidth · Egress
- 계산 : 원본 사진 사이트 15MB × 하루 1,000번 = 15GB / 웹용 사진 1MB × 1,000번 = 1GB → 사진 크기만으로 10배 넘게 차이
- 동시접속 : 같은 순간에 쓰고 있는 사람 수 (하루 방문자와 다름) — 식당 좌석 수
- 한도를 넘으면 서비스마다 다름 : 추가 요금 / 속도 제한 / 대기열 / 일시 정지 → 서비스를 고를 때 "한도와 넘었을 때"를 확인

# 05. API · API 키 (6분)

- API : 프로그램끼리 정해진 방식으로 요청하고 답을 받는 창구 — 은행 창구. 내 JavaScript → Supabase API "menus 보여줘" → 메뉴 데이터
- API 키 : 창구에 내미는 출입증
  - 공개용 키(Publishable Key) : 손님용 출입증. 웹사이트 코드에 들어가므로 누구나 볼 수 있다는 전제. 할 수 있는 일은 RLS(접근 규칙)로 제한 → STEP 04
  - 비밀용 키(Secret Key) : 사장님 마스터키. 모든 규칙 무시. 코드 · GitHub · 채팅방 · 캡처 어디에도 올리지 않기. 노출되면 새 키로 바꾸기
- AI에게 연결을 요청할 때도 "Secret Key는 사용하지 마"를 꼭 붙인다

# 06. Database · Supabase (9분)

- Database : 데이터를 표 형태로 정리해 두는 곳. Table(표) · Column(칸 이름) · Row(한 줄)
- 오늘 만들 표 menus : id · name · description · price · image_url · created_at

| name | description | price | image_url |
|---|---|---:|---|
| Cream Latte | 부드러운 크림과 에스프레소가 어우러진 시그니처 라떼 | 6500 | images/cream-latte.jpg |
| Cappuccino | 쿠키 한 조각을 곁들여 내는 진한 카푸치노 | 5500 | images/cappuccino.jpg |
| Classic Tiramisu | 진한 마스카포네 크림과 커피 향을 담은 수제 티라미수 | 7000 | images/tiramisu.jpg |
| Mellow Ade | 레몬과 허브를 사용한 상큼한 시그니처 에이드 | 6000 | images/mellow-ade.jpg |

- price는 숫자만(6500), 화면에서 6,500으로 보여 주는 일은 웹사이트가
- Supabase : Database · 회원 관리 · 파일 보관을 한 곳에서 주는 서비스. 무료 플랜으로 수업 가능
- 프로젝트 만들기 : supabase.com → GitHub 계정으로 로그인 → New project → 이름 mellow-bean · Database 비밀번호(메모) · Region Seoul → Create
- 오늘 쓰는 곳 : SQL Editor(명령 실행) · Table Editor(표 보기) · Project Settings → API Keys(키 확인)

# 07. SQL · AI에게 SQL 요청하는 법 (10분)

- SQL : Database에게 일을 시키는 언어. 외우지 않는다 — AI가 쓰고, 나는 무슨 일을 하는지 확인하고 실행한다
- 사람 말 → SQL : 표 만들기 CREATE TABLE / 넣기 INSERT / 보기 SELECT / 바꾸기 UPDATE / 지우기 DELETE
- AI에게 줄 정보 : 어떤 Database(Supabase · PostgreSQL) / 표 이름 / 칸 이름과 종류 / 하고 싶은 일 / 하면 안 되는 일 / "실행 전에 무슨 작업인지 설명해줘"
X "메뉴 테이블 만들어줘" / O STEP 01 프롬프트처럼 칸과 규칙을 적고 설명부터 요청
실행 전 최소 확인 : 표 이름이 맞나 / DELETE · DROP이 들어 있지 않나(오늘은 없어야 정상) / UPDATE에 WHERE가 있나

# 실습 STEP 04
# 웹사이트가 메뉴를 읽을 수 있게 — 접근 규칙 RLS (6분)

- RLS(접근 규칙) : 표의 각 줄을 누가 볼 · 넣을 · 바꿀 · 지울 수 있는지 정하는 규칙. 켜 두면 규칙에 없는 일은 모두 막힌다
- 비유 — 가게 진열장. 손님은 볼 수만 있고, 진열장을 여는 건 사장님만
- 오늘 규칙 : 누구나 메뉴 보기 O / 웹사이트에서 추가 · 수정 · 삭제 X

### 프롬프트 03
Supabase의 menus Table을 웹사이트에서 읽을 수 있게 접근 규칙(RLS)을 설정하고 싶어.
로그인하지 않은 방문자도 메뉴를 볼 수 있어야 하지만, 웹사이트에서 추가 · 수정 · 삭제는 할 수 없어야 해.
SQL Editor에서 실행할 SQL을 써주고, 어떤 규칙을 만드는지 먼저 쉽게 설명해줘.
menus의 데이터와 구조는 바꾸지 마.

### 프롬프트 04
MELLOW BEAN 사이트를 Supabase와 연결하려고 해. HTML · CSS · JavaScript로 된 사이트야.
@supabase/supabase-js v2를 CDN 방식으로 쓰고, 연결 정보는 supabase-client.js 파일에 따로 둬.
supabase-client.js에 SUPABASE_URL과 SUPABASE_PUBLISHABLE_KEY를 넣을 자리를 만들어줘. Secret Key는 절대 쓰지 마.
그 다음 menus Table에서 id · name · description · price · image_url을 id 순서로 불러와서 브라우저 Console에만 출력해줘.
아직 화면의 메뉴 4줄은 바꾸지 마. 오류가 나면 Console에서 알 수 있게 해줘.

# 시간이 되면 — STEP 09 가격 바꾸기 · STEP 10 나만의 메뉴

### 프롬프트 07 — 가격 바꾸기
menus에서 Cream Latte의 가격만 6800으로 바꾸는 SQL을 써줘. 다른 메뉴는 절대 바뀌면 안 돼. 실행 전에 설명해줘.
WHERE가 중요한 이유 — WHERE 없이 UPDATE하면 모든 메뉴 가격이 6800이 된다. 실행 전에 WHERE 줄을 눈으로 확인.

### 작성 틀 ① — 나만의 메뉴
menus Table에 내 메뉴를 하나 추가하는 SQL을 써줘.
name: [메뉴 이름]
description: [한 줄 설명]
price: [숫자만]
image_url: [images/파일이름.jpg — 사진이 없으면 images/cappuccino.jpg]
실행 전에 무슨 일을 하는 SQL인지 설명해줘.

# 강사용 — 자주 막히는 곳

- Console에 빈 배열 [] → RLS 규칙이 없거나 SELECT 허용이 빠짐
- "Invalid API key" → URL과 키가 서로 다른 프로젝트 것, 또는 Secret key를 붙임
- 사진만 깨짐 → image_url과 images 폴더 파일 이름이 다름 (DAY 03 STEP 01 이름표 확인)
- SQL 오류 "relation menus does not exist" → STEP 02 실행을 안 함, 또는 다른 프로젝트에서 실행
- 가격이 6500으로 보임 → 화면 표시 코드에 쉼표 처리 요청
